You are the lead engineer for **RescueFlow AI**, a 24-hour AdaHack 2026 demonstration responding to Epilog's challenge *"AI-agenti za obvladovanje nepričakovanih dogodkov pri reševalnih prevozih"*. ## Mission and nonnegotiable scope

The organizer wants **initial plan → unexpected event → revised plan** with patients/equipment/urgent tasks, multiple trips, time windows, capacity, priorities, road/air travel and dependencies. A specific example: ambulance R2 breaks down with kit K1 still inside; a different vehicle must recover it before its downstream delivery can happen. One helicopter can be grounded by fog for one hour; receiving-site capacity can change. An AI agent will orchestrate the process in stage 3.

One interviewed ambulance driver/former dispatcher described this workflow: dispatcher receives call, sees nearby available units, sends the assignment; crew receives it with Google Maps navigation already populated; crew reports problems to dispatch. This is single-practitioner testimony, not a verified nationwide API description. **Build a dispatcher decision-support layer, not a navigation app.** Model the outgoing assignment as a **mock dispatch notification**; SUMO provides all fictional routing; no Google Maps SDK/API key and no real patient data.

### Engineering contracts to establish now

1. Backend: Python 3.11+ if supported, Pydantic models (schema versioned), standard `src/` or clear importable package, organized modules. Frontend is stage 3; no frontend required yet. Install packages in a local venv; do not contaminate global Python. Dependency versions should be recorded/locked enough for reproducible operation.
2. Define canonical types: `WorldState` with `plan_revision` for planning-affecting events plus separate `telemetry_seq` for frequent simulator positions, `Vehicle`, `Task`, `Stop`, `Asset`, `ReceivingSite`, `Event`, `PlanProposal`, `PlanEvaluation`, `DispatchMessage`, `OperatorDecision`, `SimulationSnapshot`. IDs stable and times in **simulation seconds**. Distinguish wall-clock runtime from simulation time.
3. Write interfaces (Python protocols/abstract classes or equivalent): `ScenarioLoader`, `TravelTimeProvider`, `Planner` (`baseline_repair` and `optimized_repair`), `PlanValidator`, `ApprovalService`, `DispatchNotificationAdapter`, `NavigationHandoff`, `SimulationController`, `EventInterpreter` and `BenchmarkRunner`. It is fine to implement some later, but contracts must be clear, serializable, and mockable. Do not create a distributed microservices architecture.
4. Pure candidate planning: generating options must not mutate the committed world. A proposal records `based_on_plan_revision`, changed assignments, estimated stop arrival times, unserved tasks, feasibility diagnostics, and score explanation. Approval checks the **semantic planning revision** (not every one-second position telemetry tick), a short proposal TTL, current route feasibility and idempotency; **only after approval** modify committed assignments and create mock dispatch notifications. Simulation-only policy-authorized autoapproval may be added later, but must never control real assets.
5. Operator/safety invariants: no overlapping vehicle tasks; medical/crew capability matching; pickups precede deliveries; patient/equipment capacities; hospital receiving-slot limitations; locked in-progress tasks not silently reassigned; grounded helicopter unavailable; K1 location cannot jump; broken vehicle cannot move. If an occupied ambulance breaks down, escalate rather than invent a medical handoff. For the demo, R2 breaks down carrying **only equipment**, not a patient.

## Implement a functioning vertical slice

A. **Inspect environment:** detect OS, shell, git status, Python, Node, `sumo`, `netgenerate`, and available package managers. Prefer automated nonprivileged installation and `pip install eclipse-sumo` or official distribution where appropriate; verify actual executable behavior. Create `scripts/doctor` or a Python CLI `doctor` command with clear pass/fail diagnostics and exact remediation instructions.

B. **Repository and docs:** create/update `README.md`, `AGENTS.md`, `docs/ARCHITECTURE.md`, `docs/CONTRACTS.md`, `docs/DECISIONS.md`, `docs/IMPLEMENTATION_STATUS.md`, `docs/RUNBOOK.md`, `docs/SCENARIOS.md` and `docs/REQUIREMENTS_TRACEABILITY.md`. Include `.env.example` with *optional* LLM variables, never credentials.

C. **Reproducible SUMO seed:** generate a fictional connected ~7×7 street grid with traffic signals and two hospitals/receiving locations. Use `netgenerate` and deterministic background traffic generation, either checked-in small XML fixtures or a script that generates **identical demand for a given seed**. Create a **genuine smoke run** with at least one ambulance moving on an actual SUMO route; record the SUMO version and a measured duration. No pretend simulator, no hardcoded screenshots, no decorative map.

D. **Initial synthetic plan:** at least five road ambulances and one abstract helicopter; two receiving sites; about 6–10 tasks (patient pickup/delivery, urgent response, equipment pickup/delivery); multiple vehicle trips and time windows; K1 aboard R2; multiple preassigned tasks and at least two vehicles busy. HELI_1 uses an abstract 200 km/h flight model with explicitly declared startup/landing assumptions (not SUMO movement). Persist initial schedule/scenario/event timeline as stable JSON and validate feasibility *before* running experiments. Coordinates/nodes for task locations must exist in SUMO.

E. **Conventional baseline B0:** nearest **available, eligible, feasible** unit for a new urgent call; on exceptions perform local priority/deadline-ordered feasible repair, preserve unaffected commitments, reroute around closures and trigger handoff tasks where required. This is an *inspired reference policy*, **not** 'the current Slovenian algorithm'. It must include mock assignment messaging and the same assumed notification/approval/mobilization delays as enhanced methods.

F. **Enhanced A1:** deterministic full-remaining-plan insertion and local-search/swap heuristic (or OR-Tools if reliable) that can reconsider *unstarted/unlocked* tasks fleet-wide. Strict feasibility first; optimize unserved critical tasks, critical delay, other lateness, assignment churn and extra travel in that order. Provide honest alternatives under at least 'urgent-first' and 'minimum-disruption'; only return distinct feasible options, not fabricated choices. If optimization is equal/worse than baseline in a scenario, report it.

G. **Events and scenario:** implement typed `vehicle_breakdown` and `new_urgent_task` first, plus typed data models for road closure, hospital capacity, helicopter fog/grounding, and priority change even if some execution waits until prompt 2. The primary event should support the Slovenian report `Vozilo R2 je obstalo. Komplet K1 je ostal v vozilu.` but actual NLP/LLM orchestration comes in stage 3. Validate reported identities against authoritative world state. Build mock outgoing dispatch messages generated only on committed changes, with vehicle ID, task ID, destination and status.

H. **Command line and sanity check:** provide documented working commands to: doctor; load/reset scenario; run a 30–120s headless SUMO smoke; compute B0 and A1 candidates from a deterministic breakdown; list feasibility/metrics and propose/approve a selected plan; print/log mock unit notification. Avoid exact unimplemented commands in README. The planner's route ETA provider must operate on the same network as SUMO or explicitly document an interim approximation that stage 2 will replace.
