# Architecture

## Dispatcher workstation

Vite serves the React application and proxies `/api` and `/ws` to
FastAPI. Each server process owns one `DispatchRun` on a single worker
thread. Its `TraciSimulationController` holds the only live connection.
Play, step, reset, event application and approval are serialized on that
worker. Reads and WebSocket subscribers receive a published snapshot;
they share no live TraCI connection. Run IDs distinguish resets and
sequence numbers order snapshots independently of plan revisions.

Crew report extraction uses the optional OpenAI structured-response
adapter or the deterministic parser. Its bounded network request runs
outside the SUMO worker. The deterministic workflow resolves IDs and
custody against the world, computes impact, and prepares distinct
feasible proposals. Only the operator approval endpoint can commit one.

Approval validates a copy of the current world. The controller
checkpoints SUMO, installs the selected routes, and advances one step to
observe them. On failure, it restores the previous checkpoint and keeps
the prior committed plan and notifications. A failed restore pauses the
run with an error. Dashboard runs and solver logs live under
`simulation/state/dashboard/<run_id>/`. The CLI retains its original
save-state-per-command workflow described below.

This describes the code in `src/rescueflow/` as it exists today, not the
aspirational full system in `docs/DEVELOPMENT_PLAN.md` section 4. Where
they differ, this file and `docs/IMPLEMENTATION_STATUS.md` win.

## Process model

Every `rescueflow` CLI invocation (`src/rescueflow/cli/main.py`) is a
**separate OS process**; there is still no server and no frontend. State
is handed between commands two ways:

```
simulation/scenario/scenario_v1.json   the initial, validated, checked-in plan (stable)
simulation/state/world.json            the current (mutable) WorldState -- gitignored
simulation/state/proposal_*.json       saved PlanProposal objects -- gitignored
simulation/state/sumo.state.xml.gz     the live SUMO session's saved state -- gitignored
simulation/state/sim_event_log.jsonl   append-only log of stop/custody/green-wave events
simulation/state/solver_log.jsonl      append-only B0/A1 solver audit trail
simulation/network/*                   SUMO network/routes/cfg -- gitignored, regenerated by `sumo setup`
```

For pure planning (`scenario`, `event`, `plan`), this is still just JSON
files, as in prompt 1. For the **live, stepping simulation** (`sim load` /
`sim advance` / `sim breakdown` / `sim closure` / `plan approve` when a
live session exists), persistence across the process boundary uses
SUMO's own `simulation.saveState`/`--load-state` mechanism, not a kept-
alive Python process -- see docs/INTEGRATIONS.md for exactly why and the
real bugs that choice surfaced and fixed. Each `sim` command: connects
(fresh or resumed), does its one job, mirrors real positions/completions
into `WorldState`, saves state, and closes.

## Module map and data flow

```
rescueflow.scenario.loader.build_initial_world()
        |  (uses travel.SumoTravelTimeProvider for every stop ETA --
        |   nothing here is a hardcoded/decorative number)
        v
   WorldState  <----------------------------------------+
        |                                               |
        v                                               |
rescueflow.events.interpreter.RuleBasedEventInterpreter  |
   .parse(text) -> EventDraft                            |
   .validate_event(draft, world) -> ValidatedEvent | ValidationError
        |                                               |
        v                                               |
rescueflow.events.apply.apply_event(world, validated)  --+  (mutates world:
        |                                                  vehicle.status, task
        |                                                  status, new recovery
        |                                                  task, asset location;
        |                                                  bumps plan_revision)
        v
   WorldState (post-event)
        |
        +--> rescueflow.planning.baseline.BaselinePlanner.baseline_repair()   -> PlanProposal (B0)
        +--> rescueflow.planning.optimized.OptimizedPlanner.optimized_repair() -> list[PlanProposal] (A1, per profile)
        |        (both call rescueflow.planning.insertion + rescueflow.planning.validator
        |         internally; neither ever mutates `world`)
        v
   PlanProposal (feasibility + score attached)
        |
        v
rescueflow.approval.service.DefaultApprovalService.approve(world, proposal, ...)
        |  re-checks: not already committed, plan_revision match, TTL,
        |  fresh feasibility re-validation
        v
   WorldState (post-commit) + DispatchMessage(s) via
   rescueflow.dispatch.notification.MockDispatchNotificationAdapter
```

`rescueflow.sumo.controller.TraciSimulationController` is the only module
that imports `traci`. Prompt 1 implemented a genuine smoke run
(`run_smoke`). **Prompt 2 implements the full execution loop**:
`load_scenario` spawns every ambulance with stops; `step` advances the
simulation, detects dwell-begin/dwell-complete transitions
(`_process_arrivals_and_stops`), transfers asset custody and completes
tasks only on real completion (`_complete_stop`), mirrors live
edge/position into `Vehicle.sumo_edge_id`/`sumo_lane_position`
(`_update_positions`), runs green-wave signal priority (`_run_green_wave`,
delegating to `rescueflow.sumo.green_wave.GreenWaveController`), and
applies any due `ScheduledRestoration`s; `apply_committed_plan` re-routes
exactly the vehicles an approved proposal touched;
`freeze_vehicle_and_locate` physically stops a breaking-down vehicle at
its real live position and reports that position back for the recovery
task; `apply_road_closure_physically` disallows a closed edge's lanes
going forward. Nothing in the planning or approval path calls TraCI --
`events.apply`/`planning/*`/`approval/*` only ever read/write `WorldState`.

## Why a validator shared by both planners and the approval gate

`rescueflow.planning.validator.DefaultPlanValidator` is called from three
places: inside `try_insert` (every candidate insertion, by both B0 and A1),
at the end of `baseline_repair`/`optimized_repair` (final feasibility
report attached to the proposal), and again inside
`DefaultApprovalService.approve` (fresh re-check at commit time, since the
world may have moved on since the proposal was generated). This is one
piece of logic, not three -- see docs/CONTRACTS.md for exactly what it
checks and why that list is the right list.
